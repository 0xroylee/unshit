# unshit first-version acceptance agreement

English · [简体中文](unshit.zh-CN.md)

This agreement records the CLI scope and the review corrections approved in conversation. The implementation uses TypeScript and Bun, takes a development requirement as input and produces an implementation plan backed by source code. Model access reuses the local Codex login and the native App Server. The CLI does not implement the target application that the prompt asks for.

## Entry and results

```text
unshit "build an event ticketing system for a single team"
```

There is only one main command. It offers `--cwd`, `--out`, `--answers`, `--json`, `--jsonl`, `--agent`, `--turn-timeout` and optional model settings; a normal call inherits the local model configuration. There is also `--install-skill` (optionally with `--skill-dir`, `--force` and `--json`), which installs the embedded unshit agent skill into the skills directories of Claude Code and Codex. The skill runs one live `--agent` process, shows the whole brief and reference preview in chat, and relays each approval only after the user explicitly gives it. It reads the exact returned artifact path and restarts after edits or process loss, with an interactive terminal fallback. Before implementation, the agent must give the user the “Trusted, not checked” section and the open decisions, and once the open decisions are settled, unshit must plan again. After implementation, the agent must give a conformance report per task: for each named wrong implementation, the report states whether it was killed, survived, failed in a different way than expected (which does not count as killed) or was not run, and it lists the checks that actually ran separately from the checks in the plan. Progress shows the real stages in ASCII, and citations are inline in the plan. By default, unshit saves the plan, the evidence manifest and the source snapshots. When material business answers are missing, interactive mode asks for them, non-interactive mode returns a structured `needs_input`, and the reference search does not start. Interactive mode also asks a person to approve the brief before the reference search; see below.

The first version adds no separate resume/refs/export commands and introduces no SQLite, background service, plugin framework or full job-recovery protocol. It does not publish an npm package, GitHub Issues, commits or deployments.

## Brief approval (approved 2026-10-25)

The final brief is the brief rebuilt with the answers (when the rebuild fails, the intake brief, with the answers as context), or the intake brief when there were no questions. Once the brief is final, a person approves its requirements R* and acceptance criteria A*, and only then do the local scan and the reference search start. An interactive terminal run shows the brief's overview, each requirement with its acceptance criteria (marked `you said: "…"` with the user's own words, or `inferred`), the exclusions and the assumptions, and continues only when the input is `yes` (case-insensitive). Any other reply returns `needs_input` (`approvalRequested: true`) with exit code 2 and writes an answers file that contains the brief. The host knows only that someone typed `yes` at the terminal, not who it was. Ctrl+C at the prompt, or the end of input, returns `interrupted` with exit code 130; when the input ends between two questions, the next question also returns `interrupted`. Without `--agent`, a run with `--json` or `--jsonl`, or without a terminal, does not wait for approval; the plan stays Draft, and the run writes the same kind of answers file (`approveBrief: false`). If writing the answers file fails, the plan is still saved as usual and the result has no `answersFile`. `Ready` requires this approval; the completed result, the manifest and plan.md record the hash, method and time of the approval, or that there was no approval. Only the host enforces the approval: without an approval, the host keeps the plan Draft. The prompts of the plan and review turns state the approval status that the host recorded and require the model not to mark the plan Draft because of the approval and not to report a finding about it; the host does not check whether the model complies.

An answers file can carry an approved brief (`approveBrief: true`). This is not a new command and not a job-recovery protocol: a rerun still rescans the local project and again searches for and reads the reference source; it only skips intake, answering and the rebuild. The file is still bound to the hashes of the prompt, the directory and the rule version. Approval cannot replace answers: every question in the request must have an answer; otherwise, reading the file fails and lists the IDs of the unanswered questions. The brief is validated again under the intake rules and must not contain `materialQuestions`; the host reassigns R*/A* and determines the origins again. The host cannot tell who changed `approveBrief` and records the approval as `via: "answers_file"`.

## Live agent mode

`--agent` opts into JSONL stdout and stdin in one live process, implies `--jsonl`, allows redundant `--jsonl`, and rejects `--json` and `--install-skill`. Existing terminal, JSON, JSONL and answers-file calls keep their behavior. The host emits one pending `input_request` with a fresh host-issued `requestId`: `material_answers` includes a batch of unanswered questions and reasons; `brief_approval` includes the full final brief; `preview_confirmation` includes the full published snapshot, revision and exact page path. A matching `input_response` supplies exactly the nonempty requested `answers` or a boolean `approved`. Supplied answers stay in question order and are not requested again. A false brief approval stops before local scanning or research; a false preview confirmation stops before ranking, tree checks, reads or planning. The host records agent brief approval as `via: "agent"` with its own hash and time and does not claim to verify human identity. Approval and confirmation are separate gates.

Malformed, early, stale, duplicate, wrong-kind or extra-field input fails with exit 1, one fixed structured `agent_protocol_error`, no raw input echo and no downstream work after failure. A cancel record, SIGINT or EOF before completion aborts the active turn and pending request, cleans up stdin and signal listeners and the model session, and returns one final `interrupted` result with exit 130. No timeout applies to a human reply; model turn timeouts remain 124. There is no persisted resume protocol. The embedded skill obtains missing business decisions in a chat batch, shows each full brief and preview before requesting explicit approval, and relays only that approval to the current host request. It starts over for edits or a lost process and uses a visible terminal if live writable stdin is unavailable. The reference-plan rule pack and its hash are unchanged.

## Protocol and evidence boundaries

- `codex app-server` stays running. After the initialize response, the host sends `initialized`. It tells responses, notifications and server requests apart and matches the active thread/turn. Receiving `turn/completed` does not mean success; the status can also be failed/interrupted.
- The embedded skill entry point and the host constraints are passed in through `thread/start.developerInstructions`, and the detailed rules of each stage come with the input of the matching turn. `outputSchema` is submitted with every relevant turn. The read/write policy uses the protocol of the actual version and must not copy example enums that do not match.
- Plan turns are read-only and do not automatically approve writes or permission escalation. Server requests must be answered or explicitly declined; they must not be left hanging. There is no automatic replay after a disconnect and no exactly-once guarantee.
- Codex manages the native session history. unshit manages source bytes, hashes, line numbers and evidence verdicts. Session history must not stand in for evidence.
- External source code goes to the model as untrusted data. The host validates candidate IDs, paths, commits and citations, and does not accept arbitrary URLs/commands that the model generates or its claims that tests have run.
- Reads of source, tests, dependencies, CI and licenses are recorded separately; a missing file must be stated. A verification command in the plan must have a basis in a project script that was read, or be marked explicitly as created during implementation. Reading a reference test does not mean it ran and passed. The wrong implementations that the plan lists are handed to the implementer to check; unshit has not applied or run them. An adopted reference pattern must cite an excerpt of a test in that reference repository that uses this code, or state why there is none; when none of the adopted patterns cites a reference test, the plan stays Draft.
- Independent review uses a new session, and the repair loop is bounded. For each observable acceptance criterion, the reviewer tries to build a wrong implementation that no check in the plan catches. Those still not caught after the repair, and those that only a business decision can rule out, all stay in Draft; the model does not make business decisions on the user's behalf. Surviving mutants are only suggestions from the review: the host drops items it cannot use, records them as informational gaps and does not fail the run because of them. When the repair passes validation but the review after it does not complete, the plan also stays in Draft. Material gaps that cannot be removed stay in Draft. Finishing generation does not mean that the target project has been implemented or verified.
- The report lists what the plan trusts but the host has not checked: the selected reference repositories (the latest commit on the default branch at run time, the star count, the dates, test paths counted by file name, tests that were read but not run, the license evidence), the citation claims that the model wrote, local source code without a commit, and a review by the same model; that review, and the surviving mutants it reports or does not report, are all only the model's reasoning. When the plan has wrong implementations, the report gives their count and states that they were not applied or run. When the plan cites reference tests, the report gives the count of distinct reference test excerpts and states that test files are identified by path name only and were not run. When the brief has been approved, the report states whether the approval came from the terminal, agent protocol or answers file, and that the host does not know who approved it. When no reference repository was selected, the report says so directly.

## Limits of the verification record

The review in conversation read the pinned source above and the related tests and configuration, and generated the local protocol types. CLI runs, model requests, real cancellation and packaging tests were still pending when this agreement was set up; actual results go into `docs/verification.md` (in Chinese), and planned checks must not be called passed.
